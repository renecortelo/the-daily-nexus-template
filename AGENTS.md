# Working agreement

Use `docs/WORK_PLAN.md` as the canonical backlog. When reporting pending work,
read it rather than reconstructing a list from conversation or chronological notes.
Keep task IDs stable. Record additions, removals, scope/priority changes and reasons
in its change log. Do not equate implemented code with verified production benefit.
Keep deployment-specific evidence, private run data and credentials out of this file
and all shared documentation. Update status during work and after verified release.

Preserve the one-hour workflow cap, protected shutdown margin, bounded retries,
source-grounded verification and no-spend controls. Never generate/retry episodes
without explicit authorization. Functional changes must reach the private deployment
and sanitized public template through tests, privacy scans and reviewed export.
